# Design review, November 2026

This is a review of the whole design, asked for by the maintainer on 2026-11-21. It says what is sound, what went
wrong, and what the project does next. [`roadmap.md`](roadmap.md) holds the steps that follow from it.

## Verdict

- **The idea is sound, and the pure core that holds it is the best part of the code.** The state is the only truth,
  the work is derived from it by key, an incarnation drops a late answer, and a step is one transaction.
- **The runtime is built on the wrong unit.** An entity is an actor loaded in memory, and a step is computed from
  the copy in memory and written without reading what is stored. Most of the runtime exists to keep that copy the
  only one.
- **Effect Cluster was added as a second runtime on top of the first.** It is the largest source of bugs, and it
  still runs on one machine only. The goal it was added for stands, and Cluster comes back for it in a smaller part.
- **The scope grew faster than the core settled.** A log with partitions and consumers, a query engine that answers
  alike on two dialects, renames, a drain and a procedure for a full disk came before the first release.
- **The method made every decision permanent.** It found many bugs, and it never asked whether a piece should
  exist.

The tests are green: `bun test` passes 865 tests, skips 55 and fails none, in 103 seconds, on 2026-11-21. So the
trouble is not broken code. The trouble is a structure in which each fix costs a new rule.

## What the maintainer chose

The maintainer took these on 2026-11-21, after reading this review.

- The integration of Effect Cluster goes, and Cluster comes back later to assign the shards.
- The runtime is built again on the transaction, if the spike passes.
- The parked pieces are taken out, and the notes are frozen.
- The library is the server half of the Elm architecture end to end: effect-tea in the browser, entities on the
  server, and one set of schemas for both. Its first application is a slice from the browser to an entity, right
  after the base.
- A base on one process comes first. Several machines and several databases come later, and the base keeps them
  possible.

## What the library is for

The library is for whoever writes an interface in effect-tea and wants the server written the same way. That gives
it a reader no other tool serves, and a way to choose what the backend needs.

A search of 2026-11-21 found nothing that does the same: a pure `update`, work derived from the state and compared
by key, incarnations, the state in the application's own SQL and nothing replayed, as a library. It was a few
searches, and no survey. Each piece exists elsewhere.

- [XState's durable execution](https://stately.ai/docs/xstate/v6/durable-execution), of its version 6, is the
  nearest. It has pure transitions, a snapshot the application stores, and timers held in the state. It is marked
  experimental and ships no storage. It has no work compared by key and no incarnation.
- Lamdera runs the Elm architecture on both sides with shared types, in Elm, on a platform of its own. It is the
  precedent for the whole.
- [DBOS Transact](https://github.com/dbos-inc/dbos-transact) is a library that needs only PostgreSQL, as this one
  is. Its programs are functions resumed from checkpoints.
- Temporal and Restate replay a function over its history. Both document what a change of a long workflow's code
  costs, [Temporal](https://docs.temporal.io/develop/typescript/workflows/versioning) and
  [Restate](https://docs.restate.dev/services/versioning.md). A state that is stored has no history to stay
  compatible with.

So the library is new in how it joins the pieces, for a small public: TypeScript on Effect, a state written out,
and entities that last. It does not compete with a platform. Its measure is an application of the maintainer's that
runs on it.

## What is sound

- **`src/machine.ts` and `src/program.ts`.** A transition takes what is stored and an event, and gives what to
  write and what to set going. Only 8 of the 112 bugs are the machine's, and most of those are fixed.
- **The contract a program sees.** `update`, `work`, `project`, the three ways an operation is delivered, a defect
  that suspends, and a rehearsal without a database or a clock.
- **The examples.** Each reads as its use case does, which was the test of the API.
- **The rule that a claim about running code is a test.** It is the part of the method worth keeping.

## Finding 1: a step is written from memory

The runtime keeps each entity's machine in memory, steps it there, and writes the result. The statement that writes
the state names the entity and nothing else, in `write` of
[`src/storage/entities.ts`](../src/storage/entities.ts). It does not check that the row is still the one the step
was computed from. So the copy in memory must be the only copy, and everything below follows from that.

- **One runtime must own the database.** Decision 0080 holds it, with an advisory lock on PostgreSQL, a hold file on
  SQLite and a map of directories for PGlite. Each hold has a way around it: bugs 84, 85, 100 and 109, and the open
  questions on a session PostgreSQL ends, on a second runtime and on a second name of a file. A spike saw steps
  overwritten after a session was lost.
- **An entity has a life in the process.** It is loaded, unloaded, passivated, evicted, crashed and stopped, under a
  lock counted by hand. Decision 0029 was changed by eleven notes, and decision 0274 changed nine. The subject holds
  26 notes, 17 of them changed.
- **Two queues stand in line.** A caller's message waits in memory before it is stored. That gives the bound of
  callers' messages, `Full`, the record of offers of decision 0282 and a count raised by one fiber and lowered by
  another.
- **Two mechanisms fire a timer.** A loaded entity sleeps on its own timers, and the waker reads the stored ones for
  the rest. The hand-off between the two is where the waker's bugs are.
- **`settled` reads six counts kept by hand.** Each new wait must update them, and one missed update hangs it.
- **The tests need their own scheduler.** A rule of order is held by a seed, and a change that moves a yield loses
  the seeds. Decision 0292 proposes to move the process's state into a pure core for this reason.

The design gives a program one principle: work is derived from the state, and nothing starts or cancels it by hand.
The runtime does not follow it. It starts, stops, counts and cancels by hand, at each edge. A runtime that derived
what runs in the process from what is stored would need none of the bookkeeping above.

## Finding 2: Cluster is a second runtime

On one process the loop steps an entity. On Cluster a door steps it inside Cluster's transaction, and the loop steps
it too. About half of the step's path is written twice, and the two differ: one transaction for each message on one
process, one for several on Cluster.

- **Two layers of idempotency fight.** Cluster answers a retry from its own saved reply before the library sees it.
  So every answer that is no reply is reset in Cluster before a retry, and the library keeps Cluster's ids in two
  tables to delete Cluster's rows by statements of its own.
- **The library depends on what Cluster does not promise.** It reads and deletes rows of `cluster_messages`,
  `cluster_replies` and `cluster_locks`, by their names and columns, in modules marked unstable.
- **The memory may be ahead of the database.** A door's step leaves a machine not yet committed, and the next step
  tells by a count of steps whether the commit happened.
- **It buys little.** Every runner shares one file of SQLite on one machine, since Cluster has no fence. So Cluster
  gives neither more machines nor the loss of one.

Cluster holds 30 notes, 29 bugs and about a third of the open questions. No user has it, since nothing is published.

### What Cluster is for here

The maintainer asked for Cluster so that the library runs on several machines, with shards, on code the project
does not write. The goal stands. What failed is which part of Cluster was taken.

- **Cluster fits as who holds what.** Runners register, a health check drops one, and shards are assigned and moved.
  This is the hard part of several machines, and the library should not write it.
- **Cluster does not fit as the transport of a request.** The library already stores a request's reply under its
  id. Cluster's persisted messages store it again under other rules, and each layer needs a repair inside the other.
- **Cluster cannot hold a rule of correctness yet.** On PostgreSQL its lock is confirmed before a commit and not by
  it, as [`cluster.md`](cluster.md) says. The fence was asked for in
  [Effect-TS/effect#10058](https://github.com/Effect-TS/effect/issues/10058), which is open with no answer on
  2026-11-21. So decision 0084 keeps the runners on one file of SQLite, and the library runs on one machine.
- **The integration took nothing away.** `cluster.md` lists eight things Cluster gives that the runtime also does:
  the mailbox, the deduplication, the replies, the timers, the passivation, the capacity, a defect and a type not
  registered. The runtime keeps its own for six and adapts the other two.
- **A stable API would not change this.** Across four releases the notes record no change of an API that cost work.
  They record what Cluster does: a restart without end, a reply never deleted, a runner with no version, no fence.

About a quarter of the bugs of family C are not Cluster's. They belong to several processes on one database: two
versions at once in a rolling deploy, a runner that lost its shard and still acts on the world, and consumers each
runner declares for itself. They come back with several machines, whatever assigns the shards.

## Finding 3: breadth before depth, and exactness everywhere

Each feature multiplies with two dialects, two runtimes, a deploy and every point of a crash. Family A of the bugs
is a feature met by a deploy. Family D and seven other bugs are a feature met by PostgreSQL.

- **The log is a small Kafka.** Topics, partitions with a head each, publications dropped by a trigger, consumers
  with cursors, readers by partition, a reading that waits, a prune and a sweep.
- **The read model is a small query engine.** Paging by ranges of an index, `count`, `sum` and `countBy`, with an
  index of three expressions on PostgreSQL so that both dialects order alike, and a sum refused by a count of units
  of 2^980 so that both refuse alike.
- **An exact mechanism was chosen where a simple one holds.** A sender is woken by the resumption it waits for and
  never looks again, which needs a table of waits and a message `Resumed`. A reply to an operation is deleted by the
  step that ends the work, and the sweep deletes it too, since the first way races on a pool. A request under a used
  id is compared with the first message through the migrations of every version.
- **An edge got a mechanism where a refusal would do.** JSON is text on PostgreSQL because a program's data may hold
  U+0000, so no statement of PostgreSQL reads the JSON it stores.

## Finding 4: the method keeps everything

A note is never rewritten, a bug is fixed by a new rule, and a review checks each rule against the others. So the
method asks whether the rules agree, and never whether a rule should exist. It made a heavy structure consistent.

- 259 notes in three weeks, of which 59% were changed by a later one. `docs/decisions/reviews.md` is 700 KB.
- `AGENTS.md` is 29 KB, most of it on how a note and a premise are written.
- The step under way, decision 0294, moves the same rules into `docs/design.md`, `docs/premises.md` and
  `docs/rejected.md`, area by area. It keeps the mass and changes its place.
- `docs/design.md` is 162 KB. It reads as the notes laid end to end, and a reader does not find the contract in it.

The maintainer asked whether a model too weak for the design caused this. In part. The first notes are good. The
wrong turns are decision 0029, which took the actor as the form of an entity, and decision 0081, which stepped
inside Cluster's transaction. A stronger model may have questioned both. But the method would have carried either
model the same way, since no step of it removes anything.

## The direction: the transaction is the unit

**Every event is one transaction that reads the entity under a lock, steps the machine from what it read, and
writes.** The caller's fiber runs it. The database serializes the steps of one entity, by a lock of the entity's row
on PostgreSQL and by its one writer on SQLite.

1. A transaction begins, and reads the entity's row, its keys and its mailbox, and the reply stored under the
   request.
2. `Machine.step` steps the event, and then each `Handle`, until the mailbox is empty or the entity is suspended.
3. The transaction writes what the machine gives, and commits.
4. After the commit, the process starts and stops the fibers of the operations, and wakes the one fiber that sleeps
   until the earliest stored timer.

What stays in memory is what cannot be stored: the fibers of the operations that run, and for each of their entities
the machine's `running`. An entity with no operation under way has nothing in the process, and `Restart` gives its
`running` back inside the step's transaction, as an activation does today.

**What it removes.** The hold of a database, the loaded entity and its life, the queue in memory, `Full`, the
capacity, the timers of a loaded entity, `settled` and its counts, the scheduler of the tests with its pins, and the
need for a fence. Two processes on one database then lose no step, since each reads before it writes.

**What it costs.** A read and a decoding of the state at each step, where a commit already costs more. An exact
wake-up across entities becomes a retry after a wait, with a signal in the process as a shortcut.

**How it is shown false.** A spike builds it, small, before anything is deleted. The step of the roadmap says what
the spike must pass, and what the project does if it fails.

**Several machines later, on Cluster.** A step that reads before it writes is the fence the library waited for, and
the roadmap before this review already named a fence of the runtime's own as the other way. With it a runner that
lost its shard cannot write over another runner's step, on PostgreSQL as on SQLite. Cluster then comes back as who
holds what. A shard's runner runs the operations of the shard's entities and fires their timers, as decision 0162
has it. A shard held by two runners for a moment costs a second run of an operation, which an incarnation and an
idempotency key already cover. Nothing of the library's is persisted in Cluster, and no statement of the library
reads Cluster's tables. One database still bounds the whole: shards spread the work of the runners and survive the
loss of a machine, and they do not spread the storage.

## Where it must be able to go

The maintainer wants several machines and several databases in time. The base builds neither, and keeps both
possible by six rules. They are a sketch. The spike tests the first alone, and each later step checks the rules it
meets.

1. **Every write reads first.** A transaction reads the entity under a lock before it writes it, and nothing in
   memory is the truth. It keeps several machines possible.
2. **A step's transaction writes its own entity's rows alone.** It keeps several databases possible, since an
   entity's rows then lie in one of them. The storage of today breaks it in two places: the step that ends an
   operation deletes the replies its receivers keep, and a step that stores a reply reads the asker's keys.
3. **What crosses two entities is a request with an id, or a sweep.** A request is given again until it is answered.
   A sweep deletes, late, what no step may delete across entities.
4. **What runs in memory is derived from what is stored.** An operation run twice does no harm, by its incarnation
   and its idempotency key. So a shard two runners hold for a moment breaks nothing.
5. **The storage is a narrow surface.** The statements of a step are few and lie in one module, so another database
   is another module.
6. **A row says which version wrote it, and no process writes over a newer one.** It keeps a rolling deploy
   possible.

The contract a program sees already names no machine and no database. Entities talk through operations alone, and a
step is one transaction. So the six are rules of the runtime, and no program changes when the library grows.

Three limits are the model's, on any number of machines. No transaction spans two entities. One entity under many
messages is slow, since it handles one at a time. No question is asked across entities but of what the projections
show.

## Questions for the contract

Each is a rule of the contract that a simpler one may replace. None is decided here. They are read when
`docs/design.md` is written again.

- **A defect on a caller's message.** It suspends the entity today, with its timers. It could fail the request alone
  and leave the entity running, since a caller retries in either case. `discard` would then have no use.
- **The sender.** A program gives a schema of its senders, with migrations, and a reply is keyed by its version. A
  request id the boundary makes unique, and a sender carried in the message, would need none of it.
- **`Reused`.** A request under a used id that carries another message is compared through the migrations. The
  first reply could answer it, as many services do.
- **A `keep` of 0.** A retry sent before the answer is joined to the first request in memory. A least `keep` would
  need no join.
- **U+0000 in a program's data.** Refused where it is encoded, it would let PostgreSQL hold JSON as `jsonb`.

## The rules of work proposed

`AGENTS.md` is written again, short. These are its rules, beside those on language and commits, which stay.

- **One specification, kept true.** `docs/design.md` says what holds. A commit that changes a behaviour changes its
  sentence. Why a rule holds is a sentence beside it. There are no notes.
- **A rule the code keeps has a test that fails without it.** A fact about a dependency that a rule rests on has a
  spike.
- **Removing comes first.** A change asks what it can take out before what it adds. An edge is refused where it
  enters before it is given a mechanism. One job has one mechanism.
- **Budgets.** The runtime and the storage, without tests, stay under 2,500 lines together, `docs/design.md` under
  600, `AGENTS.md` under 120 and `roadmap.md` under 150. A change that crosses one is the maintainer's choice. The
  numbers are this review's, and the maintainer sets them.
- **No feature while more than ten bugs are open.**
- **What a session finds is a failing test, a bug of `docs/bugs.md` or a question of `docs/open-questions.md`.**
  A bug fixed leaves its file, and git keeps it.

## Leads this review found

None is reproduced by a test, so each is a lead and no finding. The first five are Cluster's, and go with it.

- `keepSent` of `src/storage/cluster.ts` counts the asker's keys and then inserts. On PostgreSQL the asker's step
  may end the work between the two, and no sweep reads `effecttea_sent_requests`.
- `forgetUnder` of `src/storage/cluster.ts` reads its subquery again in each of three statements.
- `forgetUnder` deletes Cluster's replies before its messages, and Cluster's `clearReplies` locks the message first.
- `PRAGMA data_version` is read on every dialect, and fails on PostgreSQL, where a reading that waits is then woken
  by no other runner.
- The comment of `src/storage/cluster.ts` says Cluster has no call that forgets a request. `deleteProcessed` exists
  at 4.1.3, and deletes by type and time.
- `indexName` of `src/storage/projections.ts` names an index by `Hash.string`, which a release of Effect may change.
  The open question on a long index name holds it.
- A rehearsal's `deploy` runs no migration, as `docs/design.md` says, so a state whose schema does not read back
  what it wrote passes a rehearsal.
